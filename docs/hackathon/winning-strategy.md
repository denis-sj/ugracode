# Стратегия победы

## Принципы

1. **Побеждает демо, а не код.** Жюри видит 5–7 минут защиты. Всё строится вокруг сценария демо.
2. **Критерии — это чек-лист.** Каждый пункт из [criteria.md](criteria.md) должен быть показан на защите явно, с подписью на слайде.
3. **Один «вау-момент» лучше десяти фич.** Для кейса 9 — живой разбор обращения с анимацией и сравнение «с ИИ против без ИИ».
4. **Цифры убеждают.** Точность классификации на тестовом наборе, время обработки, число кликов — на слайде.
5. **Надёжность демо.** Подготовленные демо-данные, запасной путь, если LLM недоступна (кэш ответов или локальная модель), и видеозапись демо на случай сбоя.
6. **Говорим языком заказчика.** Сначала боль и выгода (сокращение времени ответа, нарушений SLA), потом технологии.
7. **Показываем будущее.** Слайд «план внедрения и развития» — заказчик это просил.

## Тайминг на ~24 часа (черновик, уточнить по положению)

| Часы | Что делаем |
|---|---|
| 0–1 | Выбор кейса, спецификация, сценарий демо, вопросы ментору |
| 1–3 | Каркас: репозиторий, Docker Compose, БД, синтетические данные, дизайн-система |
| 3–12 | Ядро: ИИ-пайплайн и главные экраны |
| 12–18 | «Вау»-визуал, анимации, аналитика, отчёт о качестве |
| 18–22 | Полировка, деплой демо, презентация, видеозапись демо |
| 22–24 | **Заморозка фич**, прогон защиты 2–3 раза, загрузка на платформу |

## Как набрать максимум по критериям

Критерии и веса: [criteria.md](criteria.md). Ниже — что делаем ради каждого балла.

### Менторы (2 чекпоинта × 10 баллов, берётся среднее)

| Критерий | Как берём максимум |
|---|---|
| Проделанная работа (5) | К **чекпоинту 1** уже работает сквозной путь «текст → заявка» (пусть некрасиво) и есть дизайн экранов. К чекпоинту 2 — почти всё ядро. На каждый чекпоинт — короткий список «было → стало» и живой показ, а не рассказ. |
| Техническая реализация (5) | Показываем схему архитектуры, ИИ-пайплайн с порогом уверенности, тесты и отчёт о точности. Задаём ментору вопросы по предметной области — это и уточнение, и демонстрация вовлечённости. |

### Эксперты (17 баллов на защите)

| Критерий | Как берём максимум |
|---|---|
| Соответствие теме (4) | Закрываем **каждый** пункт критериев кейса явно и с подписью на слайде: 5–10 тестовых обращений, правильность полей и исполнителя, исправление и подтверждение диспетчером, сравнение ручных действий с ИИ и без. Демо — ровно три случая из кейса: типовое, аварийное, с нехваткой данных. |
| Технологичность (3) | ИИ-пайплайн из нескольких шагов, поиск по смыслу (эмбеддинги), порог уверенности, адаптер модели (облако ↔ локальная, ради 152-ФЗ), журнал действий, Docker. Одна схема архитектуры на слайде. |
| Качество и работоспособность (3) | Демо без падений: кэш ответов модели, заранее загруженные данные, запасное видео. Отчёт о качестве с цифрами. |
| Чёткость и структура выступления (3) | Структура: боль заказчика → сценка → живое демо → цифры → архитектура → план внедрения. Прогон с таймером 2–3 раза. Сценка — см. [../ideas/pitch-scene.md](../ideas/pitch-scene.md). |
| Демонстрация решения (3) | Живое демо, а не скриншоты. Один яркий момент («вау») + понятные цифры «с ИИ / без ИИ». |
| Распределение ролей (1) | Команда из одного человека, но **у нас есть роли**: Денис — капитан и продукт, ИИ-агенты Данкония (архитектор) и Семён (кодер) работали по процессу: задачи, спецификации, PR. Отдельный слайд «Команда 1+∞: человек + агенты» — это и балл, и сильная история. |

## Работа параллельными агентами

Решение владельца (2026-11-14): **весь проект делают ИИ-агенты, несколько агентов работают
одновременно.** Узкое место — не скорость кода, а внимание владельца и стыки между потоками.
Поэтому:

1. **Сначала контракты, потом параллель.** До запуска потоков Данкония пишет спецификацию и
   фиксирует общие контракты: схема БД, типы данных заявки, API между экраном и сервером,
   формат ответа ИИ. Без них параллельные агенты разъедутся.
2. **Один поток — свои файлы.** Две задачи, которые правят одни и те же файлы, не идут
   параллельно. В каждой задаче в `docs/tasks/` указаны папки, которые она трогает.
3. **Каждый поток — своя ветка и маленький PR.** Владелец сливает часто (раз в 1–2 часа), чтобы
   конфликты не копились.
4. **3–4 потока максимум.** Больше владелец не успеет проверять.
5. **Демо-данные и сценарий защиты — отдельный поток с первого часа**, а не в конце.
6. Пример деления для кейса 9: (а) данные + ИИ-разбор + отчёт о точности; (б) подбор исполнителя +
   поиск по базе знаний; (в) интерфейс диспетчера и дизайн-система; (г) аналитика, экран «с ИИ /
   без ИИ», позже презентация.
