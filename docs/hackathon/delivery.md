## 2. SonarQube и CI

Что уже есть:

- `sonar-project.properties`: проект `ugracode`, источники `apps`, `packages`, `modules`, тесты — `**/tests/**`,
  `**/*.test.ts(x)`; исключены `**/node_modules/**`, `**/dist/**`, `**/coverage/**`, `**/migrations/**`,
  `**/*.d.ts`, `docs/**`, `reports/**`.
- Профиль `sonar` в `docker-compose.yml` (http://localhost:9000).
- CI `.github/workflows/check.yml`: `pnpm install --frozen-lockfile` → `pnpm check` → проверка ссылок
  документации (`python3 -m unittest discover -s tests`).
- `pnpm check` = `tsc --noEmit` + ESLint (включая границы слоёв) + Vitest.

Чего нет и почему:

- **Покрытие не подключено.** В зависимостях нет `@vitest/coverage-v8`, в `vitest.config.ts` нет
  `test.coverage`, поэтому `coverage/lcov.info` не создаётся, а пути в `sonar-project.properties`
  указывают на несуществующий файл. Добавлять зависимость в этой задаче нельзя (зона — документация);
  TODO для владельца: `pnpm add -D @vitest/coverage-v8`, включить `coverage.reporter: ['lcov']`
  и `coverage.include` для серверной логики, затем добавить шаг `pnpm test -- --coverage` в CI.
  Цель из правил — не ниже 60 % для серверной логики.
- **`pnpm sonar` не существует**, хотя спецификация его упоминает. Запуск вручную:

  ```bash
  docker compose --profile sonar up -d sonar     # http://localhost:9000, admin/admin
  docker run --rm \
    -e SONAR_HOST_URL=http://host.docker.internal:9000 \
    -e SONAR_TOKEN=<токен из интерфейса> \
    -v "$PWD:/usr/src" sonarsource/sonar-scanner-cli
  ```

  Либо добавить скрипт `sonar` в `package.json` (вне зоны этой задачи).
- **Sonar не запускается в CI**: нужен `SONAR_TOKEN` в секретах GitHub и публичный/доступный
  сервер SonarQube. На хакатоне достаточно локального прогона перед сдачей — статус ❓.

Перед PR: прогнать `pnpm check`, локальный Sonar; новых Blocker / Critical / Major не сливать.

## 3. Флаги фич

Серверные модули выключаются одной переменной, приложение стартует и разбирает пример заказчика
(это проверяет тест-контракт `packages/testkit`):

```bash
FEATURES_OFF=extraction,routing,priority pnpm dev:api
FEATURES_ON=history-seed pnpm seed          # сид истории (по умолчанию выключен)
```

| Модуль | По умолчанию | Что перестанет работать при выключении |
|---|---|---|
| `extraction` | вкл | агентный разбор полей и проверка цитат |
| `priority` | вкл | приоритет и сроки по матрице |
| `routing` | вкл | топ-3 исполнителя с причинами |
| `emergency` | вкл | детектор аварии и уведомление дежурным |
| `knowledge` | вкл | инструменты базы знаний и поиск для инженера |
| `applicant-profile` | вкл | подстановка места работы из профиля |
| `reports-dashboard` | вкл | дашборд и отчёты |
| `history-seed` | выкл | демо-история 600 заявок (сид) |
| `quality` | вкл | `pnpm eval` (на разбор не влияет) |
| `example` | вкл | образец модуля (можно выключить на демо) |

Веб-модули `clarify-chat`, `dispatcher-review`, `engineer-desk` флага не имеют: их страницы
регистрируются всегда, а данные берут из API. Поэтому «выключить экран» через `FEATURES_OFF`
нельзя — это осознанное ограничение (экран без серверного модуля показывает пустое состояние).

## 4. План и описание внедрения

### 4.1 Этапы

| Этап | Срок | Что происходит | Критерий выхода |
|---|---|---|---|
| 0. Подготовка | 1–2 недели | доступ к CMDB, истории заявок, каталогу сотрудников; 30–40 реальных обращений с эталоном; согласование матрицы приоритетов и SLA | заполнен `testset/dev/`, качество перемерено на реальных данных |
| 1. Пилот на одной линии | 4 недели | система работает в режиме подсказки: ИИ разбирает, диспетчер проверяет **каждую** заявку; сбор правок и ошибок | ≥ 60 % заявок подтверждаются без правок или с одной правкой; диспетчер экономит ≥ 30 % времени |
| 2. Расширение | 2–3 месяца | интеграции CMDB, телефонии, почты, AD; включение отчётов О1–О8 и выгрузок; обучение смен | SLA и нагрузка считаются по реальным данным; жалоб на ложные аварии нет |
| 3. Промышленная эксплуатация | после пилота | SSO, резервное копирование, мониторинг, 152-ФЗ, при необходимости — локальные модели | подписан регламент, система в контуре заказчика |

### 4.2 Интеграции

| Система | Что нужно | Чем закрывается сейчас | Что делать на пилоте |
|---|---|---|---|
| CMDB | корпуса, кабинеты, оборудование, инвентарные и серийные номера, IP | `data/cmdb.json`, порт `CmdbPort` | адаптер к реальной CMDB, сверка оборудования по инвентарному номеру |
| История заявок | закрытые заявки за 3–6 месяцев: текст, поля, исполнитель, решение | синтетические 600 заявок, порт `HistoryPort` | выгрузка из текущей системы (или Excel на первом этапе) |
| Телефония / записи звонков | аудио + расшифровка | `SpeechPort`; облачные модели речи недоступны ключу (403), заглушка работает | расширить доступ Polza или поставить локальный `whisper.cpp`; интеграция с АТС |
| Почта / уведомления | письма заявителю и дежурным | таблица `notification`, экранные уведомления, порт `NotificationPort` | SMTP или корпоративный мессенджер |
| AD / SSO | вход сотрудников, роли | демо-пользователи и cookie-сессия | OIDC/LDAP, синхронизация ролей и подразделений |
| Справочники и регламент | типы услуг, категории, приоритеты, SLA, признаки аварий | `data/dictionaries.json`, `data/priority-matrix.json`, `data/emergency-rules.json` | согласовать с заказчиком, вынести в админку |

### 4.3 Закрытый контур

Локальные модели в этой версии не разворачивались (решение владельца): все порты уже абстрагированы,
для контура РФ достаточно заменить адаптеры — LLM 7–8B на сервере с GPU (или Apple M2 16 ГБ для пилота),
`whisper.cpp` для речи, локальные эмбеддинги при возврате к поиску по смыслу.

### 4.4 Обучение диспетчеров

- 2 занятия по 60 минут: «как читать разбор и след агента», «когда править, когда подтверждать».
- Инструкция на 2 страницы: что означает уверенность, что делать при низкой, как вернуть заявку,
  как объявить аварию, где журнал.
- Правило пилота: **любая** заявка подтверждается человеком; ошибки ИИ разбираются на еженедельной
  пятиминутке и превращаются в статьи базы знаний или правила.

### 4.5 Метрики пилота

| Метрика | Как считаем | Цель пилота |
|---|---|---|
| Доля заявок, подтверждённых без правок | журнал: подтверждение без изменения полей | ≥ 60 % |
| Точность полей и выдуманные поля | `pnpm eval` на реальном наборе | поля ≥ 90 %, выдуманных = 0 |
| Время диспетчера на заявку | счётчик действий и таймер | −30 % к ручному сценарию |
| Попадание исполнителя в топ-3 | `pnpm eval` + фактические назначения | ≥ 90 % |
| SLA: доля в срок | отчёты О3 | не ниже текущей |
| Ложные и пропущенные аварии | сверка с регламентом | пропусков 0 |
| Удовлетворённость диспетчеров | короткий опрос раз в 2 недели | ≥ 4 из 5 |
