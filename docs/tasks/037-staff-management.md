Решение владельца (2026-11-14): **обязательно**. Подбор исполнителя опирается на компетенции и загрузку, значит,
руководитель должен управлять этими данными из системы, а не из JSON. UX: **краткий, минималистичный, понятный**.

## Что сейчас

- Инженеры лежат в `data/engineers.json`, отдаются только на чтение (`GET` исполнителей в `apps/api/src/server.ts`).
  Загрузка (`openTickets`) = max(сид, реально назначенные открытые заявки).
- Вкладки «Исполнители» у роли `manager` нет (`apps/web/src/shell/lib.ts`), прав на запись у неё нет
  (`packages/contracts/src/domain.ts`).

## Что сделать

1. **Данные в БД.** Инженерный профиль (отдел, линия, навыки с уровнем, здания, смена, доступность) хранится в БД;
   JSON остаётся только сидом для первого заполнения. Подбор исполнителя читает из БД. Решение по таблице — в PR
   (либо новая `engineer_profiles`, либо расширение `users`), без отдельного обсуждения.
2. **API (только `manager` и `admin`):** создать сотрудника, изменить профиль (навыки, здания, смена, доступен /
   в отпуске), деактивировать. Новый разрешающий ключ доступа, например `staff.manage`; схемы входа — в
   `packages/contracts` (zod). Валидация: ФИО, отдел из справочника, навыки из справочника.
3. **Журнал действий.** Каждое создание и правка — событие аудита: кто, что, было → стало. Видно в «Журнале».
4. **Подбор исполнителя.** Недоступный или неактивный инженер в топ-3 не попадает. Новый инженер сразу
   участвует в подборе без перезапуска.
5. **Интерфейс — минимум действий:**
   - у роли `manager` появляется вкладка «Исполнители» (тот же экран, что у диспетчера, плюс управление);
   - одна кнопка **«Добавить сотрудника»** → боковая панель-выдвижение, не модальное окно;
   - в панели 5 полей: ФИО, отдел, линия, навыки (чипы, выбор из справочника, уровень 1–5 кликом), смена;
     опциональное «здания» свернуто; одна кнопка «Сохранить», без шагов и мастеров;
   - правка существующего: клик по карточке → та же панель; переключатель «Доступен» прямо на карточке;
   - пустые и ошибочные состояния понятны одной строкой; после сохранения карточка появляется с анимацией,
     без перезагрузки и без лишних подтверждений;
   - анимации по [правилам](../rules/animations.md); светлая тема; стили через токены `packages/ui`.
6. **Тесты:** API (успех, нет прав, невалидные поля, дубликат), подбор (недоступный не предлагается, новый
   инженер появляется), аудит записывается, интерфейс (открытие панели, сохранение, права по ролям).
7. **Документация:** карта фичи в `docs/map/features/`, шаг в `docs/hackathon/demo-script.md`
   («руководитель добавляет инженера → он сразу в топ-3 с объяснением»), запись в `docs/history/`.

## Критерии готовности

- Руководитель добавляет инженера за ≤ 30 секунд; новый инженер сразу виден в подборе исполнителя.
- Диспетчер, инженер и заявитель не видят и не могут вызвать управление сотрудниками (проверено API-тестом).
- Каждое изменение есть в журнале с «было → стало».
- Нет новых замечаний SonarQube уровня Blocker/Critical/Major; `python3 -m unittest discover -s tests` проходит.
- Проверено в браузере на демо-сценарии.
