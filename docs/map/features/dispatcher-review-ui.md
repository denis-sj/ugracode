Веб-часть `dispatcher-review`: очередь `/queue` (4.3) и проверка заявки по шагам `/review?id=…` (4.4).
Серверные маршруты — [dispatcher-api.md](dispatcher-api.md). Интерфейс не считает заявки сам:
фильтры, сортировка, сроки, уверенность и «что сделать» — чистые функции `format.ts`.

## Очередь `/queue`

Данные: `GET /api/tickets?limit=200` — номер, статус, приоритет, категория, исполнитель, сроки, `createdAt`,
`updatedAt`, `isEmergency`.

- **Сводка:** ждут проверки (`in_review`), ждут заявителя (`waiting_applicant`), активные аварии
  (`isEmergency` вне архива), за смену (созданы сегодня). Цифры — `queueSummary`.
- **Состав очереди:** без явного статуса закрытые, отменённые и решённые не показываются; с
  `#/queue?status=closed` архив открывается явно.
- **Фильтры:** `Segmented` «Все / Сомнительные / Готовые / Аварии» + `SearchField` по номеру, категории и месту.
  «Сомнительные» — есть `needsReview` или минимальная уверенность ниже 75 %; «Готовые» — `in_review` без
  сомнений и без аварии. Уверенность и спорные поля берутся из `GET /api/tickets/:id` для первых 24 строк
  (кэш в `loadedDetailsRef`), запросы идут параллельно.
- **Query из hash:** `#/queue?status=in_review`, `?emergency=true`, `?assignee=u-1` применяются как начальные
  фильтры (`queueFiltersFromQuery`); сброс фильтров очищает их в интерфейсе. Ссылки с дашборда работают без
  правок дашборда.
- **Сортировка:** `sortTickets` — авария → критическая → высокий → средний → низкий, внутри уровня по
  ближайшему сроку; новые строки временно поднимаются наверх (`promoteNew`) и въезжают со вспышкой.
- **Таблица:** `PriorityMark` (круг-доля), обращение (заголовок из полей, номер, место), уверенность тонкой
  шкалой (жёлтая ниже 75 %), «ждёт» от создания, «что сделать» точкой-статусом. Аварийная строка — красная
  полоса слева; выбранная — акцентная.
- **Живое обновление:** `EventSource('/api/events/stream')`; событие с `ticketId` (известным или новым) ставит
  тихую перезагрузку в очередь (debounce 400 мс), `appeal.created` без заявки игнорируется. При ошибке SSE
  источник закрывается и включается опрос `GET /api/tickets` раз в 15 с; при уходе со страницы всё
  закрывается. Редьюсер — `queueEventAction`.
- **Превью справа:** `Sticker` с исходной цитатой (до 240 символов), 3–5 ключевых полей с `OriginBadge`,
  кандидат из `GET /api/m/routing/candidates/:ticketId` (имя из `/api/users`, score и причины).
  «Подтвердить Enter» → `POST /api/tickets/:id/confirm` с верхним кандидатом; «Открыть» → `#/review?id=…`.
  Если кандидата нет, кнопка неактивна и отправляет в проверку.

`Enter` на выбранной строке подтверждает заявку, `Space`/`Enter` на невыбранной — открывает превью.

## Проверка `/review?id=…`

`id` читается из query (`reviewTicketId`); `WebPageProps.query` прокидывает `AppShell`. Данные:
`GET /api/tickets/:id`, `/events`, `/analysis`, `/api/users`, `/api/m/routing/candidates/:id`.

- **Шаг 1. Обращение.** Оригинал с подсветкой цитат (`highlightQuotes`), след
  «Нашёл → Сверил → Спросил → Вам» (`traceSteps`): сначала `analysis.fields[*].trace`, если его нет — из
  `TicketField.trace` и происхождения полей. Строки сгруппированы по этапам; неизвестные виды отбрасываются.
  Ниже — «почему такой приоритет» (авария или `impact × urgency`).
- **Шаг 2. Поля.** `groupTicketFields`: внутри группы сначала `needsReview`, затем по возрастанию уверенности.
  Поле показывает значение, `ConfidenceBar`, `OriginBadge`, `QuoteChip`; для справочника — `select` из
  `GET /api/meta`, для остальных — ввод. `PATCH /api/tickets/:id/fields/:key`; после сохранения поле и журнал
  перечитываются, при `origin: human` видно «исправил диспетчер · ИИ предлагал …». Внизу — последние три
  правки из журнала «ИИ → человек» (`journalRows` + `diffValues`).
- **Шаг 3. Исполнитель.** Топ-3 кандидатов с score и полосой; выбранный показывает причины (похожие заявки,
  загрузка, смена, корпус). Если кандидатов нет — `select` инженеров из `/api/users`.
- **Шаг 4. Ответ заявителю.** Локальный шаблон `replyTemplate` из номера, инженера и срока; редактируется.
  **Не отправляется:** `replyDraft` и маршрута сообщений в API пока нет — в интерфейсе стоит пометка.
  «Вернуть заявителю» скрыта до модуля сообщений (009).
- **Итог справа:** `ProgressScale` (4 сегмента), ключевые поля через `DetailRow`, `ActionCounterPill`
  с числом действий (`useActionCounter`, К4), сроки по регламенту.
- **Подтверждение:** `POST /api/tickets/:id/confirm`; `Enter` (вне полей ввода) подтверждает и назначает.
  После успеха — `Modal` «Заявка назначена» с переходом к следующей (в очередь) или «Остаться».
  Кнопка активна только в `in_review`, при праве `tickets.confirm` и выбранном исполнителе.

## Клавиатура

| Клавиша | Где | Что делает |
|---|---|---|
| `Enter` | очередь | подтверждает выбранную заявку верхним кандидатом |
| `Space` / `Enter` | строка очереди | открывает превью |
| `Enter` | проверка | подтверждает и назначает (вне `input`/`textarea`/`select`) |
| `Enter` | спорное поле | открывает правку; в редакторе — сохраняет |
| `Esc` | редактор | отменяет правку |
| `Tab` | проверка | ходит только по спорным полям (`needsReview`) |

## Что не поддержано API

- `replyDraft` и отправка ответа заявителю — шаг 4 только локальный шаблон (модуль 009).
- Переход `in_review → waiting_applicant` в таблице переходов есть, но кнопка «Вернуть заявителю» скрыта:
  сообщение заявителю отправить нечем.
- Уверенность и `needsReview` не отдаются списком: очередь догружает детали первых 24 строк (кэш).
- `emergency`-вердикт с признаками и чек-листом в карточке не хранится; на проверке показывается
  `analysis.emergency`, если он есть, иначе — только `ticket.isEmergency`.
- Массовость и инциденты — отдельный экран/модуль, в очередь не встроены.

## Как проверить

```bash
pnpm dev:api
pnpm dev:web
npx vitest run modules/dispatcher-review apps/web packages/ui
npx vite build --config apps/web/vite.config.ts
```

1. Войти диспетчером → `#/queue`; фильтры и поиск, клик по строке — превью.
2. `#/queue?status=in_review&emergency=true` — фильтры применились из query.
3. «Открыть» → `#/review?id=…`; шаги 1–4, правка спорного поля, выбор исполнителя.
4. `Enter` или «Подтвердить и назначить» → модалка «Заявка назначена».
5. Вернуться в очередь: строка обновилась, авария и новые заявки приходят по SSE.
