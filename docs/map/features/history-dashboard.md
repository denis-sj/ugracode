Статус: active
Дата: 2026-11-14
Связано: [../README.md](../README.md), [../../specs/case9-core.md](../../specs/case9-core.md#39-отчёты), [../../specs/case9-features.md](../../specs/case9-features.md), [../../specs/case9-ui-design.md](../../specs/case9-ui-design.md), [../../hackathon/case9-brief.md](../../hackathon/case9-brief.md), [../../history/2026-11.md](../../history/2026-11.md)

Два модуля: `history-seed` наполняет базу синтетической историей за 6 месяцев, `reports-dashboard`
считает по ней отчёт О0 и рисует экран руководителя. Оба работают через `KernelStore`; своих таблиц нет.

## Файлы

## История заявок

- Данных 600 заявок за 6 месяцев от `clock.now()`. День выбирается взвешенно по дню недели
  (понедельник — 2,2 против 1,1–1,35 в остальные будни, выходные почти пустые), час — 8–18
  с пиком 9–11 и 14–16. Корпус — по нагрузке (ПРОМ реже офисных), кабинет — из CMDB этого
  корпуса; часть обращений по печати в корпусе Б тянется к «больному» принтеру 312.
- Особые заявки: 3 аварии (`isEmergency`, приоритет `emergency`) и 7 обращений по принтеру
  из `cab-b-312` (берётся из CMDB по кабинету 312). Остальные — случайные категории из
  `data/dictionaries.json`.
- Статусы: закрытые и решённые, ~13 % отменённых, 4 открытые. Время решения хранится в
  `payload.resolutionMinutes` события `ticket.status.changed` — отдельной колонки `resolvedAt` в контракте нет.
- Исполнитель выбирается из `data/engineers.json` по подразделению категории и корпусу;
  техника — из `data/cmdb.json` по типу и корпусу. Ссылки на инженеров, категории и технику
  проверяются тестом.
- `locationId` строится по формуле `cab-<код корпуса>-<кабинет>` — так же, как в
  `packages/db/src/seed/load-data.ts`; по нему отчёт считает корпуса и горячие точки без чтения полей.

## Отчёт О0

Параметры: `days` (1–365), либо `from`/`to`; фильтры `category`, `assigneeId`, `channel`,
`building`, `status` сочетаются. Результат: период и такой же прошлый период, итоги и ▲/▼,
среднее время решения, разрезы по приоритетам (все 5 уровней, включая нули), категориям,
корпусам, исполнителям и статусам, тепловая карта «день × час» (Пн–Пт, 8–17), топ-5 горячих
точек (корпус + кабинет) и тексты `insights`: `summary`, `priorities`, `heatmap`, `sla`,
`hotspots.meaning/action`.

- Цифры считает код. Тексты — шаблоны по фактам; ИИ-вывод подключается агентом `analyst`
  (задача 021), до него блок честно подписан «вывод собран по фактам шаблоном».
- SLA: нарушением считается закрытая заявка, решённая позже `slaDueAt`, и открытая, у которой
  срок уже прошёл. «В срок, %» — доля закрытых без нарушения.
- `facts()` отдаёт 9 коротких пар label/value — только их увидит модель, когда появится вывод.
- Фильтр по каналу читает `appeal` каждой заявки периода (в `ticket` колонки канала нет);
  без фильтра обращения не читаются.

## Экран

`/dashboard` для manager/admin по дизайну [case9-ui-design.md](../../specs/case9-ui-design.md), раздел 4.7:

- **Шапка экрана:** hero-заголовок 34–40 px с градиентом текста (`ugra-page-title`), подпись о
  сравнении с прошлым периодом. Периоды «Смена / 7 дней / 30 дней / Квартал» — стеклянная капсула
  `ugra-liquid`; рядом выбор дат (начало и конец, конец дня включается в запрос).
- **Запрос:** `GET /api/m/reports-dashboard/overview`; при пресете — `?days=…`, при датах —
  `?from=…&to=…`, фильтры `category`, `assigneeId`, `channel`, `building`, `status` сочетаются.
  Смена периода/дат или фильтра перезапрашивает отчёт.
- **Плитки:** «Обращений», «Открытых», «Аварий», «В срок», «Решение, среднее». Крупная цифра,
  ▲/▼ к прошлому периоду цветным **текстом** (зелёный — лучше, красный — хуже), не фоном.
  Клик по плитке ведёт в очередь `#/queue`; очередь пока не читает фильтры из адреса — ❓ передать
  `status`/`emergency` в задаче очереди.
- **График по приоритетам:** пять столбиков в токенах приоритетов (без библиотек графиков),
  легенда и блок «Что это значит» из `insights.priorities`. Пустой период показывает пустое состояние.
- **Тепловая карта «день × час»:** Пн–Пт, 8–17, интенсивность — `color-mix` от `--color-accent`,
  подпись «Что это значит» из `insights.heatmap`, отдельное пустое состояние.
- **Горячие точки:** таблица с корпусом/кабинетом, числом заявок и долей; блоки
  «Что это значит» и «Что сделать» из `insights.hotspots`. Цифры считает код, подпись честно
  говорит, что вывод собран шаблоном.
- **Фильтры:** категория и корпус — из справочников `/api/meta`; исполнитель — из `byAssignee`
  ответа (список не схлопывается после выбора), канал — из meta, статус — из контракта.
- **Меню «Выгрузить»:** Excel, PDF, CSV, почта и еженедельная сводка нарисованы, но все пункты
  `disabled` с подсказкой «появится с отчётами О1–О8»: серверных маршрутов выгрузки нет,
  маршруты не выдумываем.
- **Стили:** только классы и токены `packages/ui` (`var(--color-…)`, `var(--space-…)`,
  `--shadow-…`, `--dur-…`); своих цветов и «сырых» длительностей нет, фон — общая светлая тема.
- **Виджеты** `dashboard.tiles` и `dashboard.main` показываются на стартовом экране роли; при
  самостоятельном показе сами грузят отчёт за 30 дней.

## Точки входа

| Что | Где |
|---|---|
| Сид истории | `modules/history-seed/server/index.ts` → `seedHistory` через `KernelStore` |
| Генератор без базы | `generateHistory(input)` в `modules/history-seed/server/generator.ts` |
| Отчёт по HTTP | `GET /api/m/reports-dashboard/overview?days=30&category=printer` |
| Отчёт как `ReportDef` | `overviewReport` (`dashboard.overview`) в `modules/reports-dashboard/server/index.ts` |
| Экран | `#/dashboard`, компонент `DashboardPage` |
| Виджеты | слоты `dashboard.tiles`, `dashboard.main` |

## Проверки

```bash
npx vitest run modules/history-seed modules/reports-dashboard
npx tsc --noEmit
npx eslint modules/reports-dashboard/web modules/reports-dashboard/tests
npx vite build --config apps/web/vite.config.ts
```

- генератор: два прогона с одним зерном совпадают, 600 заявок, ≥6 обращений по принтеру в 312,
  ровно 3 аварии, валидные ссылки, рабочие часы, доля отмен 10–15 %, пик в понедельник;
- сид: 600 заявок в `MemoryStore`, повторный запуск не удваивает, события и обращения на месте;
- отчёт: пустая база, одна заявка, авария + просрочка + топ горячих точек, период и прошлый
  период, фильтр канала, тепловая карта, непустые `facts` и `insights`;
- форматирование: дельты ▲/▼ (рост/падение/ноль/нет прошлого), числа с разрядами, проценты,
  диапазон дат, высота столбиков, пустая и непустая тепловая карта;
- фильтры и выгрузка: селекты из meta/ответа, стабильный исполнитель, все пункты выгрузки
  `disabled` с подсказкой, сборка запроса с датами и пресетом;
- тест-контракт обоих модулей.

## Особенности и что осталось

- `history-seed` — данные, а не фича: `enabledByDefault: false`, но `pnpm seed` добавляет его
  в список сида всегда (`packages/db/src/seed/index.ts`), иначе демо-база осталась бы без истории.
- Экран использует `@ugra/ui` (`Card`, `InsightBlock`, классы `ugra-card`, `ugra-liquid`) и токены
  светлой темы из `packages/ui/src/tokens.css`. В `apps/web/vite.config.ts` нужны алиасы `@ugra/ui` и
  `react` — они приходят с веткой оболочки; без них веб-модуль не собирается в бандл.
- Горячие точки показывают корпус, кабинет, число заявок и долю. Названия оборудования и
  простой в отчёте не выводятся: в `ticket` нет ни названия техники, ни времени простоя —
  нужен джойн с CMDB или колонка, это отдельная задача.
- Выгрузка и «присылать сводку» ждут серверных маршрутов; сравнение с прошлым периодом уже
  считается (`previousTotals`, `deltas`).
- Клик по плитке ведёт на `#/queue` без параметров: очередь не разбирает query-фильтры. ❓ добавить
  фильтр очереди по статусу/аварийности в задаче очереди — тогда ссылка станет точной.
- Категории и корпуса фильтров берутся из `/api/meta`, но если менеджер не получил meta, в список
  попадают значения из ответа отчёта. Исполнители приходят только из `byAssignee`: отдельного
  справочника исполнителей в `/api/meta` нет.

## Дашборд D2 (2026-11-14)

Экран руководителя приведён к утверждённому макету `13-dash4-D2`: пять стеклянных карточек
приоритетов (число, «+N к прошлому», доля, мини-столбцы по дням, мягкий оттенок приоритета)
и три плитки — «Сейчас в работе» (труба по открытым статусам), «Закрыто в срок» (полоса с целевой
отметкой и ссылкой на шторку), «ИИ оформил без правок» (доля и «диспетчер правит 1 из N»).
Клик по нарушениям SLA открывает **правую шторку на самом дашборде** (`OverdueDrawer`):
причина из `insights.sla`, группы по исполнителям, список открытых просрочек и копирование списка.

Данные, которых не хватало, добавлены контрактом и сервером (обратно совместимо):
`byPriority[].daily`, `previousByPriority`, `aiEffect`, `slaTargetPercent`, маршрут `/overdue`.
Цель SLA 90 % — из `data/settings.json` (допущение, отмечено в `docs/knowledge/limitations.md`).
Удалены: абзац-пояснение, dev-подпись про агента `analyst`, тепловая карта и горячие точки
с дашборда (живут в отчётах), старые пять плиток метрик и виджет `dashboard.main`.
