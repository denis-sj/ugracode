# Карта фичи: оценщик качества (014)

Статус: active
Дата: 2026-11-14
Связано: [../README.md](../README.md), [../../specs/case9-agent-harness.md](../../specs/case9-agent-harness.md), [../../specs/case9-core.md](../../specs/case9-core.md#310-оценка-качества), [../../history/2026-11.md](../../history/2026-11.md), [../../history/2026-11.md](../../history/2026-11.md)

`pnpm eval` гоняет контрольный набор через тот же `PipelineEngine`, что и демо, и считает оценщики
раздела 5 харнесса. Результат — таблица «эталон / ИИ» в `reports/quality.md` (её владелец переносит
на слайд), полные траектории в `reports/eval-<дата-время>.json` и строка в `reports/quality-history.md`
(дата, модель, версия промпта, 11 оценщиков — слайд «как росла точность»). Экран 14 «Качество ИИ»
(К2) читает последний отчёт и умеет прогнать набор заново в режиме заглушки: страница `/quality`
для руководителя и админа, маршруты `GET /api/m/quality/report` и `POST /api/m/quality/run`.

## Как работает

1. `runEval()` грузит `data/*.json` (реестр полей, справочники, CMDB, матрица приоритета, инженеры)
   и собирает шаги `coreSteps()` + `modules/registry.server.ts`; регистры собираются один раз на прогон.
2. На каждый кейс — свой `MemoryStore`, `KernelEventBus` и `PipelineEngine`. Обращение: `id: eval-<кейс>`,
   текст из файла, канал из `channel`, автор — «Заявитель (прогон)» с ролью `applicant`.
3. Заглушка модели: `StubLlm` со сценарием из `testset/stubs/NN.json` (номер — из имени файла кейса).
   Запись приводится к `submit` агента `intake`: `fields`, `emergency` из `aspects.emergency`,
   `summary` из `aspects.summary.text`, `clarify: null`. Если в записи есть поля без цитаты, `check()`
   её отклоняет — второй ход сценария повторяет `submit` без них (как исправление модели по ошибке).
4. `--model <id>` или `--cloud` → `createPorts({ …process.env, AI_MODE: 'cloud', LLM_MODEL_MAIN: id })`.
   Ключа нет — прогон честно уходит в заглушку и пишет предупреждение в отчёт.
5. Из черновика собирается `ObservedRun`: поля с цитатами и `origin`, приоритет, авария (вердикт
   `draft.emergency` или мнение агента `draft.ext.extraction.emergency.suspected`), топ исполнителей,
   статьи (`draft.knowledge` + `kb_get_article` из шагов), вопрос (`clarify` или вопрос агента),
   вызванные инструменты и их число.
6. Оценщики `metrics.ts` дают попадания, промахи и выдуманные поля; `summarize()` собирает доли,
   медианы и список невыполненных порогов.
7. `scripts/eval.ts` печатает таблицу, пишет `reports/quality.md` и `reports/eval-<дата>.json`,
   дописывает строку в `reports/quality-history.md`; код выхода 0 даже при невыполненных порогах
   (провал порога — результат прогона, а не ошибка запуска).

Пороги (раздел 5.2 харнесса, в `THRESHOLDS`): поля ≥ 90 %, выдуманные поля 0, пропуски аварии 0,
приоритет ≥ 90 %, исполнитель топ-1 ≥ 70 % и топ-3 ≥ 90 %, статья ≥ 80 %, вопрос ≥ 80 %,
траектория 100 %, медиана ≤ 8 с и ≤ 0,30 ₽.

## История настройки

Раздел 5.4 харнесса: видно, как росла точность от прогона к прогону. `reports/quality.md` остаётся
последним прогоном, а `reports/quality-history.md` копит строки — по одной на `pnpm eval`.

| Колонка      | Откуда                                                                                                                                                              |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Дата         | `run.startedAt` (ISO), по ней же история сортируется: новые сверху                                                                                                  |
| Модель       | `run.model`: `stub` или id модели из `--model`/`--cloud`                                                                                                            |
| Промпт       | `promptVersion(readFileSync('modules/extraction/prompts/intake.v2.md'))` — первые 8 символов sha256; файла нет — «—»                                                |
| Набор        | имя папки набора и число обращений: `cases (10)`; `--case 01` даёт `cases (1)`                                                                                      |
| 11 оценщиков | `summary.evaluators` (`display`) в порядке `HISTORY_METRICS`: поля, выдуманные, авария, приоритет, топ-1, топ-3, статья, вопрос, траектория, медианы времени и цены |
| Порогов      | `summary.met` из `summary.withThreshold`: строка «7 из 11»                                                                                                          |

- Запись: `appendHistory(existing, historyRow(run, { prompt }))` — читает файл (или пустую строку),
  разбирает таблицу, ставит новую строку первой и рендерит заново. Дубль — совпадение
  **дата + модель + версия промпта**: повторный прогон того же запуска не плодит строк.
- Чтение: `parseHistory(markdown)` устойчиво к битым строкам — пропускает заголовок, разделитель,
  строки с неверным числом колонок, без даты/модели и без счётчика «X из 11».
- Числа не пересчитываются: строка хранит готовые `display` из сводки, поэтому таблица и отчёт
  не расходятся. Для графика на слайде берётся колонка «Поля» (или любая другая) по датам.
- Промпт версионируется содержимым файла: правка `intake.v2.md` меняет хэш и даёт новую строку
  даже при той же модели — это и есть «одна правка → прогон» из цикла настройки.

## Экран «Качество ИИ» (14)

Страница `/quality` (роли `manager`, `admin`) — утверждённый макет `Quality.dc.html`:
«Прогнать набор», таблица 10 обращений × 7 колонок (поля, выдуманные, приоритет, авария,
исполнитель, статья, вопрос) и сводка оценщиков с порогами.

| Что         | Как                                                                                                                                           |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Загрузка    | `GET /api/m/quality/report` → `readQualityReport()`: файла нет — `{empty: true}`, битый файл — пустая страница с пометкой в `notes`           |
| Прогон      | `POST /api/m/quality/run` → `runEval({ limit: 10 })` в режиме `stub` (записанные ответы `testset/stubs`, без сети), ответ — `reportFromRun()` |
| Ограничения | не больше 10 кейсов, таймаут 60 с, повторный запуск поверх идущего — ошибка «Прогон уже идёт»                                                 |
| Таблица     | `cellState()`: ✓ верно, ✕ ошибка, ? нет эталона; клик по строке раскрывает эталон/ответ ИИ, выдуманные поля, статью и шаги                    |
| Сводка      | `metricRows()` и `thresholdState()`: порог выполнен / не выполнен / нет эталона; оговорка «10 обращений, синтетика» всегда на экране          |
| Анимации    | `data-reveal` на заголовке, `useListMotion` на строках таблицы; тёмная тема — токены `@ugra/ui`                                               |

Право `reports` (а не отдельное `quality`) выбрано намеренно: экран открывает руководитель,
у которого нет прав диспетчера, а прогон — такое же чтение отчёта, как остальные отчёты О-серии.

## Точки входа

| Что                            | Где                                                                                                                                                                   |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pnpm eval`                    | `package.json` (`tsx scripts/eval.ts`)                                                                                                                                |
| Один кейс с трассировкой       | `pnpm eval --case 04` → `runEval({ caseId })`, печать `run.cases[0].trace`                                                                                            |
| Оценщики как функции           | `metrics.ts`: `evaluateFields`, `evaluatePriority`, `evaluateEmergency`, `evaluateAssignee`, `evaluateArticle`, `evaluateQuestion`, `evaluateTrajectory`, `summarize` |
| Прогон без CLI (тесты, отчёты) | `runEval({ dirs, model, cloud, caseId })`                                                                                                                             |
| Отчёт                          | `renderQualityReport(run)` / `renderConsole(run)`, `evalReportJson(run)`                                                                                              |
| Экран                          | `QualityPage` (`modules/quality/web/QualityPage.tsx`), чистые функции — `modules/quality/web/format.ts`                                                               |
| API экрана                     | `GET /api/m/quality/report`, `POST /api/m/quality/run` — `modules/quality/server/index.ts`                                                                            |
| История настройки              | `historyRow(run, { prompt })`, `appendHistory(existing, row)`, `parseHistory(markdown)`, `promptVersion(content)`                                                     |
| Регистрация модуля             | `modules/registry.server.ts` — одна строка `quality`; веб-часть — `modules/registry.web.ts`, строка `qualityWeb`                                                      |

## Проверки

```bash
npx vitest run modules/quality
npx tsx scripts/eval.ts            # создаёт reports/quality.md, reports/eval-<дата>.json и строку в reports/quality-history.md
```

- сравнение полей: `exact` без нормализации, `normalized` без регистра и «ё», `none` — поле не оценивается;
- выдуманные поля: нет в эталоне, цитаты нет в тексте, нет цитаты; значения из CMDB (`origin: 'cmdb'`) — не выдумка;
- пропуск: пустое поле эталона, промах приоритета, пропуск аварии, промах исполнителя и статьи;
- агрегаты: все пороги выполнены / не выполнены, «—» без эталона и это не провал;
- мини-прогон на двух кейсах во временной папке: успешный кейс, мусорный эталон, битый файл в `skipped`;
- история: round-trip «рендер → разбор», дубли по дате+модели+версии, битые строки, пустая история;
- экран: разбор реального `reports/quality.md` (шапка, 11 оценщиков, кейсы, подробности, оговорки),
  пустой и битый markdown, свежий прогон с лимитом 10, клетки ✓/✕/? и состояния порогов;
- тест-контракт модуля и сквозной прогон с выключенным модулем.

## Особенности

- `example.extract` (модуль-образец) пишет `building`, `cabinet`, `equipment` правилами. Если в эталоне
  этих ключей нет, поле считается выдуманным — набор должен описывать все поля, которые видит диспетчер.
- Статью в прогоне пока выбрать нечем: у модуля `knowledge` только инструменты, шага выбора статьи нет,
  а агент `intake` инструменты базы знаний не имеет. Оценщик статьи честно показывает 0 %, пока не
  появится шаг выбора (`knowledge.select`).
- `data/engineers.json` не проходит схему `modules/routing/contracts.ts` (`level: "first_line"` — строка,
  схема ждёт число), поэтому подбор идёт по `DEMO_ENGINEERS` (`u-eng-*`) и топ-3 не совпадает с эталоном
  (`u-engineer-*`). Это данные и модуль `routing`, не оценщик.
- Авария оценивается по вердикту `draft.emergency` или по мнению агента: модуль `emergency` в реестр
  ещё не включён, поэтому приоритет «Авария» код пока не выставляет.
- Настроечного набора `testset/dev/` нет — об этом сказано в самом отчёте, чтобы цифры не выдавали
  за настройку по большому набору.
