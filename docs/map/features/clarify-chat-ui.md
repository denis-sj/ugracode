## Обращение (4.1)

1. **Старт.** По центру «Что случилось?», подзаголовок и большое стеклянное поле с примером.
   Под полем: скрепка (фото или скриншот), микрофон, телефон и круглая графитовая «отправить».
   Заголовок старта — 76 px (`--text-hero`), поле — 760 px по центру, примеры обращения — чипами.
2. **Отправка.** `POST /api/appeals { text, channel: 'chat', attachments }`; пока идёт разбор —
   переливающаяся строка «Разбираю обращение». Сразу после ответа открывается
   `GET /api/appeals/:id/stream`, шаги пайплайна появляются по мере прихода; после `run.completed`
   берутся `GET /api/tickets/:id` и `GET /api/tickets/:id/analysis`.
3. **Ответ ИИ** — обычный текст без пузыря, ключевое жирным (`**…**` → `<strong>`). Сообщения
   заявителя — справа, в графитово-фиолетовом пузыре.
4. **Карточка-вопрос.** Заголовок, «1 из N» со стрелками, варианты с номерами (до трёх),
   подписи под вариантами, «Не знаю — диспетчер уточнит сам», строка «Свой вариант»,
   «Пропустить» и «Ответить · Enter». Выбранный вариант подсвечен рамкой и отправляется Enter,
   ↑/↓ двигают выбор; «Не знаю» больше не выбирается по умолчанию (Enter не отправит пустой ответ),
   а если модель не дала вариантов — они добираются из справочника поля, чтобы карточка не была пустой.
   Набор текста в поле ввода клавиатурные сокращения не перехватывают.
5. **Стикер «Ваше обращение»** появляется после первого ответа ИИ и заполняется по ходу:
   «уточняем…» → значение с подписью происхождения («из вашего текста», «из профиля»,
   «сверено с базой», «ждём ваш ответ», «оценил ИИ»), статус, шкала «Собрана → Проверена → Назначена → Выполнена»
   (компонент `ProgressScale`, `in_review` — два сегмента, `assigned` — три), в конце — инженер и срок.
   Если `analysis.emergency` подтверждена или под вопросом — красная пульсирующая точка,
   «Авария · 97%» и цитата-признак в подсказке. Стикер **не** дублируется в ленте чата.
6. **Финальная реплика** — когда вопросов не осталось: номер заявки и что будет дальше.
   Номер и срок берутся из заявки, ничего не выдумывается.

### Ход разбора (SSE)

`useRunStream` открывает `EventSource` после создания обращения. `reduceRunEvent` превращает
`step.started` / `step.progress` / `step.completed` в список шагов: подпись берётся по `stepId`
(таблица `RUN_STEP_LABELS`), шаги уникальны и сохраняют порядок, сообщение шага показывается рядом.
`run.completed` и `run.failed` завершают поток; неизвестный тип события состояние не меняет.

Сервер пока запускает пайплайн синхронно и отдаёт историю разбора одним пакетом — поэтому шаги
показываются с паузой 160 мс: данные настоящие, темп презентационный. Если поток не ответил за 12 секунд,
экран берёт заявку через `GET /api/tickets/:id` (запасной путь), а `run.failed` показывает плашку
«Повторить». После завершения загружаются `GET /api/tickets/:id` и `GET /api/tickets/:id/analysis`.

### Откуда берутся вопросы

Источник вопросов — `analysis.missing` из `GET /api/tickets/:id/analysis`: их формулирует модель,
порядок серверный, варианты — из `missing[].options` (не больше трёх). Если `missing` пуст или разбор
не сохранился, работает прежняя клиентская сборка из `GET /api/meta` и полей заявки:

- обязательное поле пустое и у него есть `FieldDef.ask` — вопрос по шаблону;
- поле заполнено, но `needsReview: true`, и у него есть варианты справочника — просим подтвердить,
  текущее значение стоит первым с подписью «ИИ предлагает — подтвердите»;
- заполненное поле «на проверку» без вариантов не спрашиваем — его проверит диспетчер;
- на поле ответили (в том числе «не знаю»/«Пропустить») — повторно не спрашиваем;
- варианты — только из справочника (`dictionary`/`optionsFrom`), максимум три, значения — коды;
  свободный текст разрешён строкой «Свой вариант».

Если `missing` есть, но на все вопросы уже ответили, к шаблонам экран не откатывается: лишних вопросов нет.

Подписи вариантов (3.5) строятся по `origin`: «Указан в вашем профиле», «Сверено с базой оборудования»,
«Указано в обращении», «Исправил диспетчер».

Ответ на существующее поле сохраняется через `PATCH /api/tickets/:id/fields/:key` и обновляет стикер.
Если серверного поля ещё нет, ответ остаётся в локальном состоянии карточки и стикера — так демо
не падает на незаполненном API.

### Голос, файлы, звонок

- **Микрофон** активен только в браузере с `MediaRecorder` и доступом к микрофону. Нажатие пишет звук,
  остановка отправляет base64 в `POST /api/transcribe` и вставляет распознанный текст в поле.
  Нет записи или доступа — кнопка неактивна, запись не имитируется.
- **Скрепка** — одна точка входа для фото и скриншота: открывает выбор картинки, распознаёт её
  (`POST /api/screenshot`) и кладёт текст в поле обращения. Отдельной кнопки «Скриншот» и списка
  фиктивных вложений больше нет: в макете у поля три иконки, и вложения только имитировались.
- **Телефон** — ссылка `tel:` на номер диспетчерской (в демо-данных номер условный).

## Мои заявки (4.2)

- Переключатель «Активные · N / Закрытые · N» в стеклянной капсуле.
- Сверху — заявка в статусе `resolved`: номер, дата, заголовок, шкала, инженер и кнопки
  «Да, всё работает» (`→ closed`) и «Вернуть инженеру» (`→ in_progress`). Обе — `POST /api/tickets/:id/transition`.
- Ниже — строки: название, номер и статус цветным текстом, шкала из четырёх сегментов, исполнитель и срок.
- Данные — `GET /api/tickets?limit=50` + `GET /api/tickets/:id` для заголовка и полей; имена — `GET /api/users`.
- Пустые состояния для обеих вкладок, скелетоны загрузки и плашка ошибки с «Обновить».

## Дизайн

- Все цвета, стекло, кнопки, шкалы и анимации — из `packages/ui`; своих цветов модуль не задаёт.
- Стеклянные карточки, графитовые главные кнопки, акцент только на выбранном и ссылках.
- Анимации: появление снизу, выезд стикера, перелив «Разбираю обращение», плавная шкала;
  `prefers-reduced-motion` отключает всё.
- Сетка 80 px на экране обращения — едва заметная, как в макете.

## Отклонения и что осталось

- **Серверного модуля `clarify-chat` по-прежнему нет.** Вопросы уже берутся из `analysis.missing`, когда
  он есть; ответы не запускают повторный разбор (`rerun`) и не пишут след «спросили → ответили» на сервере.
  Когда появится модуль сообщений (`POST /appeals/:id/messages`), ответы пойдут в него, а не только в
  `PATCH` существующего поля и локальный стикер.
- **SSE — история, а не живой поток.** `POST /api/appeals` ждёт окончания пайплайна, поэтому события
  приходят пакетом; `useRunStream` показывает их с паузой. Когда бэкенд начнёт отдавать ответ до разбора,
  очередь перестанет накапливаться без правок интерфейса.
- **Подтверждение выполнения у заявителя** работает: роль `applicant` получила право
  `tickets.transition`, переходы `resolved → closed` и `resolved → in_progress` разрешены.
- Загрузка скриншотов и телефония — кнопки без полной серверной логики (см. выше).
- Профиль заявителя — заглушка `#/profile`: состав ещё не утверждён владельцем.

## Как проверить

```bash
pnpm dev:api
pnpm dev:web
npx vitest run apps/web packages/ui
npx vite build --config apps/web/vite.config.ts
```

1. Войти заявителем (например, «Денис Соколов»).
2. `#/chat` → отправить «в 312 кабинете не печатает принтер HP».
3. Ответить на карточки цифрами или кликом; стикер справа заполняется.
4. `#/tickets` → активные заявки, шкала, инженер и срок; закрытые — во второй вкладке.
5. Кнопка истории в шапке открывает панель справа.

- `apps/web/tests/clarify-format.test.ts` — статусы, шкала, группировка истории, вопросы и варианты,
  подписи происхождения, `**жирный**`, пустые состояния.
- `apps/web/tests/clarify-run.test.ts` — редьюсер SSE (шаги, дубли, завершение, неизвестный тип),
  `parseAnalysis`, вопросы из `missing` vs реестра, обновление стикера.
- `packages/ui/tests/ticket-format.test.ts` — форматирование статуса, этапов (`stageSegments`), сроков и истории.

## Журнал работы ИИ (задача 035)

- `POST /api/appeals` с `async: true` отвечает сразу (`appealId`, `ticketId`, `runId`), разбор идёт в фоне; без флага поведение прежнее.
- Агент пишет `agent.step` в шину дважды: `phase: 'running'` перед инструментом и `phase: 'finished'` с итогом. API (`apps/api/src/agent-trace.ts`) превращает их в безопасные события SSE: человеческая подпись, короткий итог (≤100 символов, без почт/UUID/инвентарных номеров), время; `blocked/error` — нейтрально.
- `modules/clarify-chat/web/RunTrace.tsx` — раскрывающаяся строка под сообщением: шеврон, `aria-expanded`, `useListMotion`, `aria-live="polite"`. Пока идёт разбор — «Разбираю обращение» и текущий шаг; после — «Разобрал за N с · ход работы».
- Свёрнута по умолчанию, раскрытое состояние не сбрасывается. Темы — токены, шрифт 14 px, узкий экран переносит итог.
- Тесты: `apps/api/tests/agent-trace.test.ts` (safe-фильтр и статусы), `apps/web/tests/clarify-run.test.ts` (редьюсер журнала, формат времени).

Проверить: `#/chat` → отправить обращение → нажать «Разбираю обращение» → шаги идут по ходу → после «Разобрал за N с» список остаётся раскрытым.

**Статус после первого разбора** исправлен: `applyAnalysis` сохраняет `waiting_applicant`, если в черновике остались вопросы.

## Композиция по макету (2026-11-14)

Экран приведён к референсам владельца (`01-applicant-chat-start`, `02-applicant-chat-dialog`):
старт — заголовок `--text-hero`, поле 760 px с тремя иконками и примеры-чипы; диалог — сетка
`1fr / 380px` (лента слева, заявка справа), поле ввода одной строкой внизу колонки, лента
прокручивается к карточке-вопросу, чтобы кнопка «Ответить» всегда была видна. Все светлые
оверрайды `html:not([data-theme='dark'])` из модуля удалены — обе темы читают одни правила.

## Раунд 2 правок владельца (2026-11-14)

- Шаги разбора — одна свёрнутая строка «Разбираю обращение · шаг» и «N шагов»; полный список
  и галочки только при раскрытии; отдельный список шагов из ленты удалён (`uniqueStepsByLabel`).
- Страница чата занимает остаток высоты оболочки (`flex`), прокручивается только лента,
  поле ввода закреплено внизу.
- Стикер заявки — отдельный слой (`chat-sticker-slot`): на широком экране висит справа от
  колонки чата и не участвует в раскладке, на узком встаёт над полем ввода; появляется только
  после отправки, анимация `stickerSlap` из `motion.ts`, при `prefers-reduced-motion` — без неё.
- Номера заявок — `formatTicketNumber` из `@ugra/ui` («№ 601»).
- «Мои заявки»: статус — подпись над полосками хода.
