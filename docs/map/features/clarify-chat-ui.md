## Обращение (4.1)

1. **Старт.** По центру «Что случилось?», подзаголовок и большое стеклянное поле с примером.
   Под полем: скрепка, микрофон, телефон и круглая графитовая «отправить».
2. **Отправка.** `POST /api/appeals { text, channel: 'chat', attachments }`; пока идёт разбор —
   переливающаяся строка «Разбираю обращение». После ответа берётся `GET /api/tickets/:id`.
3. **Ответ ИИ** — обычный текст без пузыря, ключевое жирным (`**…**` → `<strong>`). Сообщения
   заявителя — справа, в графитово-фиолетовом пузыре.
4. **Карточка-вопрос.** Заголовок, «1 из N» со стрелками, варианты с номерами (до трёх),
   подписи под вариантами, «Не знаю — диспетчер уточнит сам», строка «Свой вариант»,
   «Пропустить» и «Ответить Enter». Цифры 1–4 на клавиатуре выбирают вариант, стрелки листают вопросы.
   Набор текста в поле ввода клавиатурные сокращения не перехватывают.
5. **Стикер «Ваше обращение»** появляется после первого ответа ИИ и заполняется по ходу:
   «уточняем…» → значение, статус, шкала «Собрана → Проверена → Назначена → Выполнена»,
   в конце — инженер и срок. Стикер **не** дублируется в ленте чата.
6. **Финальная реплика** — когда вопросов не осталось: номер заявки и что будет дальше.
   Номер и срок берутся из заявки, ничего не выдумывается.

### Откуда берутся вопросы

Пока серверный модуль `clarify-chat` (задача 009) не влит, список вопросов собирается на клиенте
из `GET /api/meta` и полей заявки:

- обязательное поле пустое и у него есть `FieldDef.ask` — вопрос по шаблону;
- поле заполнено, но `needsReview: true`, и у него есть варианты справочника — просим подтвердить,
  текущее значение стоит первым с подписью «ИИ предлагает — подтвердите»;
- заполненное поле «на проверку» без вариантов не спрашиваем — его проверит диспетчер;
- на поле ответили (в том числе «не знаю»/«Пропустить») — повторно не спрашиваем;
- варианты — только из справочника (`dictionary`/`optionsFrom`), максимум три, значения — коды;
  свободный текст разрешён строкой «Свой вариант».

Подписи вариантов (3.5) строятся по `origin`: «Указан в вашем профиле», «Сверено с базой оборудования»,
«Указано в обращении», «Исправил диспетчер».

Ответ на существующее поле сохраняется через `PATCH /api/tickets/:id/fields/:key` и обновляет стикер.
Если серверного поля ещё нет, ответ остаётся в локальном состоянии карточки и стикера — так демо
не падает на незаполненном API.

### Голос, файлы, звонок

- **Микрофон** активен только в браузере с `MediaRecorder` и доступом к микрофону. Нажатие пишет звук,
  остановка отправляет base64 в `POST /api/transcribe` и вставляет распознанный текст в поле.
  Нет записи или доступа — кнопка неактивна, запись не имитируется.
- **Скрепка** открывает выбор файлов и показывает имена вложений; имена уходят в `attachments`
  при создании обращения. Загрузки файлов на сервер пока нет — это отдельная задача про скриншоты.
- **Телефон** — ссылка `tel:` на номер диспетчерской (в демо-данных номер условный).

## Мои заявки (4.2)

- Переключатель «Активные · N / Закрытые · N» в стеклянной капсуле.
- Сверху — заявка в статусе `resolved`: номер, дата, заголовок, шкала, инженер и кнопки
  «Да, всё работает» (`→ closed`) и «Вернуть инженеру» (`→ in_progress`). Обе — `POST /api/tickets/:id/transition`.
- Ниже — строки: название, номер и статус цветным текстом, шкала из четырёх сегментов, исполнитель и срок.
- Данные — `GET /api/tickets?limit=50` + `GET /api/tickets/:id` для заголовка и полей; имена — `GET /api/users`.
- Пустые состояния для обеих вкладок, скелетоны загрузки и плашка ошибки с «Обновить».

## Дизайн

- Все цвета, стекло, кнопки, шкалы и анимации — из `packages/ui`; своих цветов модуль не задаёт.
- Стеклянные карточки, графитовые главные кнопки, акцент только на выбранном и ссылках.
- Анимации: появление снизу, выезд стикера, перелив «Разбираю обращение», плавная шкала;
  `prefers-reduced-motion` отключает всё.
- Сетка 80 px на экране обращения — едва заметная, как в макете.

## Отклонения и что осталось

- **Серверный `clarify-chat` ещё не влит.** Поэтому вопросы строятся по шаблону `FieldDef.ask`, а не по
  `missing`/аспекту модели; ответы не запускают повторный разбор (`rerun extract`) и не пишут след
  «спросили → ответили» на сервере. Когда появится модуль, `buildQuestions` заменится на данные
  `MissingField`/сообщений чата, а ответы пойдут в его маршруты.
- **Подтверждение выполнения у заявителя.** Кнопки честно вызывают `POST /api/tickets/:id/transition`,
  но текущая таблица прав в `packages/contracts` не даёт роли `applicant` права `tickets.transition`
  (переход `resolved → closed` при этом разрешён). До правки ядра сервер отвечает 403 — интерфейс
  показывает ошибку. Это блокер демо-сценария а7, чинится в контрактах/ядре (вне зоны этой задачи).
- Загрузка скриншотов и телефония — кнопки без полной серверной логики (см. выше).
- Профиль заявителя — заглушка `#/profile`: состав ещё не утверждён владельцем.

## Как проверить

```bash
pnpm dev:api
pnpm dev:web
npx vitest run apps/web packages/ui
npx vite build --config apps/web/vite.config.ts
```

1. Войти заявителем (например, «Денис Соколов»).
2. `#/chat` → отправить «в 312 кабинете не печатает принтер HP».
3. Ответить на карточки цифрами или кликом; стикер справа заполняется.
4. `#/tickets` → активные заявки, шкала, инженер и срок; закрытые — во второй вкладке.
5. Кнопка истории в шапке открывает панель справа.

- `apps/web/tests/clarify-format.test.ts` — статусы, шкала, группировка истории, вопросы и варианты,
  подписи происхождения, `**жирный**`, пустые состояния.
- `packages/ui/tests/ticket-format.test.ts` — форматирование статуса, этапов, сроков и истории.
