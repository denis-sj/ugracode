# Правила: качество кода (под проверку SonarQube)

Статус: active
Дата: 2026-11-14
Связано: [testing.md](testing.md), [git-and-deploy.md](git-and-deploy.md), [../hackathon/criteria.md](../hackathon/criteria.md)

Меняются только с «ок» владельца.

Код оценивают менторы и **SonarQube + ИИ** ([../hackathon/criteria.md](../hackathon/criteria.md#3-код)).
Машина видит весь репозиторий, поэтому каждый мусорный файл и каждое замечание стоят баллов.

1. **Ноль багов и уязвимостей по SonarQube.** Перед каждым PR прогонять анализ локально
   (SonarQube в Docker или SonarLint в редакторе). Новые замечания уровня Blocker/Critical/Major не сливать.
2. **Никаких секретов в коде.** Ключи только через переменные окружения, в репозитории — `.env.example`
   с пустыми значениями. Секрет в коде — это уязвимость в отчёте SonarQube.
3. **Без дублирования.** Повторяющийся кусок больше ~10 строк выносить в общую функцию или компонент.
4. **Короткие функции.** Цель — функция до ~40 строк, когнитивная сложность до 15 (порог правила Sonar).
5. **Строгая типизация.** TypeScript в `strict`, без `any`; в Python — аннотации типов.
6. **Линтер и форматтер обязательны** (ESLint + Prettier или Ruff), запускаются в CI. Предупреждения не копить.
7. **Покрытие тестами.** Отчёт о покрытии подключить к SonarQube. Цель — не ниже 60% для серверной логики
   (ИИ-пайплайн, подбор исполнителя, расчёт SLA).
8. **Нет мёртвого кода**: закомментированных блоков, `console.log`, `TODO` без номера задачи, неиспользуемых импортов и файлов.
9. **Сгенерированное и чужое не коммитить**: `node_modules`, сборки, дампы, большие файлы данных.
   Демо-данные — небольшие seed-файлы.
10. **Понятная структура** по слоям (интерфейс → API → сервисы → доступ к данным), описанная в
    [../map/README.md](../map/README.md). Её же показываем менторам как «архитектурную логику».
11. В корне репозитория — `README.md` с запуском одной командой, архитектурой и ссылкой на демо.
    Его читают и менторы, и ИИ-оценщик.
