══════ ЗАДАЧА 1. Качество разбора К2 до порогов ══════
Почему: критерий К2 «проверить, правильно ли ИИ заполняет поля и определяет исполнителя». Сейчас порогов выполнено 7 из 11.

Текущее состояние (reports/quality.md, прогон 2026-11-14, модель deepseek/deepseek-v4.1-flash-1017):
- Поля 84 % при пороге ≥ 90 %.
- Выдуманные поля 9 при пороге 0.
- Приоритет 80 % при пороге ≥ 90 %.
- Время на обращение (медиана) 14,8 с при пороге ≤ 8 с.
- Остальное проходит: авария без пропусков (но 1 ложная тревога в case-10), исполнитель топ-1 89 %, топ-3 100 %, статья 100 %.

Что сделать:
1. Запусти `pnpm eval` и сохрани базовый прогон (он сам попадёт в reports/quality-history.md).
2. Разбери провалы из reports/quality.md, раздел «Провалы по оценщикам». Главные причины на сейчас:
   - case-01: поле department пустое, эталон «dep-it».
   - case-02, case-04: ИИ пишет «корпоративная почта» / «сеть и интернет» вместо «почта» / «сеть» (поле object).
   - case-03, 04, 05, 06: поле symptoms — ИИ дописывает лишнее вокруг формулировки обращения.
   - Выдуманные поля: equipment «Компьютер» (case-03), serviceType «repair» (case-04), equipment «сервер» (case-05) и ещё 6 — ИИ заполняет поле, которого в тексте нет.
   - Приоритет неверный: case-07 и case-10; в case-10 ещё ложная авария.
3. Правь только промпт и шаги разбора: modules/extraction/prompts/intake.v1.md (делай новую версию v2, не затирай v1), при необходимости шаги в
   modules/extraction/server и modules/priority. Правила для промпта: заполнять поле только если оно есть в тексте или найдено в справочнике/CMDB;
   symptoms — короткая выдержка из обращения без добавлений; object — из словаря значений; защита от «поставь высший приоритет» остаётся.
4. Время: сократи число шагов агента и лишние вызовы модели, убери последовательные вызовы там, где их можно выполнить параллельно.
   Если ≤ 8 с недостижимо на выбранной модели, не подгоняй — опиши причину и варианты (другая модель, кэш) в отчёте владельцу.
5. После каждой правки — `pnpm eval`. Остановись, когда выполнено 11 из 11 порогов или после 5 итераций; в отчёте приведи таблицу «было → стало».
6. Обнови docs/knowledge/limitations.md таблицей из нового прогона. Тесты на изменённые шаги: успех и каждая ветка ошибки.

Готово, когда: пороги из reports/quality.md выполнены (или честно объяснено, какие нет и почему), reports/quality.md и quality-history.md обновлены.

══════ ЗАДАЧА 2. SonarQube и покрытие тестами ══════
Почему: код оценивают менторы и SonarQube + ИИ (docs/hackathon/criteria.md, раздел 3). Сейчас покрытие не подключено,
результат SonarQube не зафиксирован.

Что сделать:
1. Покрытие: `pnpm add -D @vitest/coverage-v8`; в vitest.config.ts включить coverage с reporter lcov (файл coverage/lcov.info) и include для
   серверной логики (apps/api, packages, modules/*/server). Добавь скрипт `test:coverage` в package.json и шаг в .github/workflows/check.yml.
   Цель: не ниже 80 % покрытия (порог стандартного Quality Gate «Sonar way» для нового кода), минимум 60 % для серверной логики по docs/rules/code-quality.md.
   Дубли — не более 3 %, все новые Security Hotspots проверены. Если ниже — допиши тесты на непокрытые ветки в приоритетных модулях.
2. SonarQube локально: docker compose --profile sonar up -d sonar (http://localhost:9000). Токен создаёт владелец в интерфейсе SonarQube —
   попроси его: «создай токен в SonarQube и пришли мне / положи в переменную SONAR_TOKEN». Токен в репозиторий не коммить.
   Добавь скрипт `sonar` в package.json (запуск sonar-scanner через docker run, как описано в docs/hackathon/delivery.md, раздел 2).
   В sonar-project.properties убери TODO про lcov.
3. Прогони анализ. Исправь все замечания уровня Blocker, Critical, Major в коде приложения. Дубли, мёртвый код, секреты — исправить.
4. Мусор, который уже найден: 6 вызовов console.log вне тестов в packages/db/src/migrate.ts и packages/db/src/seed/index.ts —
   заменить на process.stdout.write или общий логгер. Новых console.log и TODO без номера задачи не добавлять.
5. Занести результат в docs/hackathon/delivery.md (строки 13 и 14: статус, дата, цифры) и приложить скриншот или текст отчёта в reports/.
6. САММАРИ ПО SONARQUBE. Сразу после ПЕРВОГО прогона (до исправлений) и ещё раз после ПОСЛЕДНЕГО составь файл reports/sonarqube-summary.md.
   Данные бери только из самой платформы SonarQube (интерфейс или её API на http://localhost:9000, например /api/issues/search и /api/measures/component),
   ничего не выдумывай. В файле:
   - дата и время прогона, версия коммита, статус Quality Gate (Passed / Failed);
   - таблица метрик: Bugs, Vulnerabilities, Security Hotspots, Code Smells, Coverage, Duplications, Maintainability / Reliability / Security rating, строки кода;
   - количество замечаний по серьёзности: Blocker, Critical, Major, Minor, Info;
   - «Минусы кода, которые нашла платформа»: топ-10 типов замечаний (правило Sonar, сколько раз, пример файла и строки, одним предложением чем плохо);
   - файлы с наибольшим числом замечаний (топ-10);
   - что исправлено: таблица «было → стало» по всем метрикам выше;
   - что НЕ исправлено и почему (если осталось замечание — укажи правило, файл и причину);
   - как воспроизвести: команды запуска.
   Файл должен быть понятен человеку, который не читал код. Верни владельцу короткую выдержку (5–8 строк) в отчёте.

7. ДОПОЛНИТЕЛЬНЫЕ ПРОВЕРКИ (организаторы не назвали платформу точно, поэтому закрываем то, что проверяют любые платформы). Запусти через npx, без добавления
   в зависимости проекта, и допиши результаты в reports/sonarqube-summary.md (раздел «Другие проверки»):
   - `pnpm audit` — уязвимости в зависимостях (High и Critical исправить или обосновать);
   - поиск секретов: `docker run --rm -v "$PWD:/repo" zricethezav/gitleaks:latest detect --source=/repo` (npx для gitleaks не работает) — секретов в коде и истории быть не должно;
   - дубли: `npx jscpd apps packages modules` — выше 3 % устранить;
   - `pnpm typecheck` и `pnpm lint` без предупреждений;
   - лишнее в репозитории: закомментированный код, неиспользуемые файлы и экспорты, большие дампы, .env — убрать.
   Платформы, которые организаторы могли бы использовать вместе или вместо SonarQube (угадываем и закрываем заранее). Запускай только то, что работает
   локально без платы и без регистрации; что не запустилось — запиши в отчёт, не выдумывай результат:
   - Semgrep (правила OWASP / TypeScript): `docker run --rm -v "$PWD:/src" semgrep/semgrep semgrep --config auto /src/apps /src/packages /src/modules` (pipx на машине нет) — уязвимости и небезопасные паттерны;
   - Trivy (зависимости, секреты, конфиги Docker): `docker run --rm -v "$PWD:/src" aquasec/trivy fs /src` — High и Critical исправить;
   - Qodana (JetBrains): `docker run --rm -v "$PWD:/data/project" jetbrains/qodana-js` — только если запускается без лицензии;
   - CodeQL (GitHub code scanning): включается только если репозиторий публичный — запиши в отчёт как «возможно, при открытии репозитория»;
   - SonarCloud / Codacy / DeepSource: облачные, бесплатны для публичных репозиториев — не подключать, но привести код к тем же правилам.
   По каждому инструменту в отчёте: найдено до, исправлено, осталось и почему.

Готово, когда: lcov создаётся, покрытие ≥ 80 % (минимум 60 %), дубли ≤ 3 %, SonarQube прогнан, Quality Gate «Sonar way» Passed, Blocker/Critical/Major = 0, delivery.md обновлён, есть reports/sonarqube-summary.md с данными «до» и «после».
