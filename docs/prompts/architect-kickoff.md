# Промпт: старт сессии архитектора (кейс 9)

Статус: active
Дата: 2026-11-14
Связано: [../../AGENTS.md](../../AGENTS.md), [../hackathon/case9-brief.md](../hackathon/case9-brief.md), [../tasks/004-core-contract.md](../history/2026-11.md), [brainstorm-kickoff.md](brainstorm-kickoff.md), [feature-intake.md](feature-intake.md)

Порядок сессий (обновлено 2026-11-14): **брейншторм ([brainstorm-kickoff.md](brainstorm-kickoff.md)) и
архитектура (этот промпт) идут параллельно** → новые фичи из брейншторма встраиваются по
[feature-intake.md](feature-intake.md) → кодеры работают по задачам.

Архитектура не ждёт итога брейншторма. Ядро и обязательные функции уже известны из брифа. Всё, что
придумаем потом, должно добавляться как модуль, а не переделкой ядра.

Как использовать: открыть новую сессию в папке репозитория и вставить текст из блока ниже целиком.

```text
Ты Данкония — архитектор проекта (роль в AGENTS.md: идеи, спецификации, планы, задачи; код не пишешь).

КОНТЕКСТ
Хакатон «Код Югры», ~24 часа, уже идёт. Команда «1+∞» — один человек (Денис), весь код пишут ИИ-агенты,
3–4 агента работают параллельно. Цель — 1-е место. Кейс 9 «Диспетчерская с ИИ» (ООО «Газпром трансгаз
Сургут», ИТ-служба): обращение (чат, голос, скриншот) → поля с цитатами → приоритет по регламенту →
авария (по содержанию и массовости) → исполнитель → база знаний → проверка человеком → отчёты.
Такой системы у заказчика нет — делаем с нуля, без интеграций.

ГЛАВНОЕ ТРЕБОВАНИЕ К АРХИТЕКТУРЕ — РАСШИРЯЕМОСТЬ
Владелец ПРЯМО СЕЙЧАС параллельно с тобой придумывает фичи. Они будут прилетать весь хакатон и после
него (проект должен вырасти в продукт). Поэтому:
- Новая фича = новый модуль в своей папке + одна строка регистрации. Ядро при этом не правится.
- Если для фичи приходится править ядро — это сигнал, что не хватает точки расширения; добавь её в ядро
  один раз, а не «костыль под фичу».
- Каждая фича отключается флагом (для демо: выключили сырое — ничего не сломалось).
- Расширяемость не должна стоить скорости: никаких микросервисов, очередей и абстракций «на вырост»
  без потребителя. Модульный монолит + чёткие интерфейсы.

УЖЕ РЕШЕНО (не переобсуждать)
- TypeScript везде, бэкенд на Node.js. Фреймворки и библиотеки выбираешь ты (предложение — в environments.md).
- Модели ИИ: облако — провайдер Polza (ключ только в .env); локально — LM Studio (LLM 7–8B) и whisper.cpp
  на Apple M2 16 ГБ. Ментор: закрытый контур — идеал, облако — запасной режим.
- Демо на ноутбуке владельца, копия на его сервере. Запуск одной командой (Docker Compose).
- Приоритет № 1 — критерии кейса К1–К5. Код оценивает SonarQube: strict TS, тесты, без дублирования.
- Значения полей — только из справочников; у каждого поля цитата-основание; приоритет по регламенту,
  не по эмоциям; авария — два сигнала (правила + модель) и массовость; ничего не уходит без человека;
  журнал действий только на добавление.

ТОЧКИ РАСШИРЕНИЯ, КОТОРЫЕ ДОЛЖНЫ БЫТЬ В ЯДРЕ (проработай каждую: интерфейс, где лежит, как регистрируется)
1. Контракты — единый источник. Пакет общих схем (например, zod): из него типы TS, JSON Schema для
   ответа модели, валидация API, типы для фронта. Поменял схему — компилятор показывает все места.
2. Пайплайн разбора — список шагов. Шаг = { id, что читает, что пишет, run(ctx) }. Порядок и включение —
   в конфиге. Новый анализ (тональность, скриншот, дубликаты) = новый шаг, ядро не трогаем. Каждый шаг
   стримит прогресс в интерфейс (SSE) и пишет след «откуда взято» (цепочка «нашёл → спросил → диспетчеру»).
3. Доменные события. Ядро публикует события (обращение создано, поле извлечено, авария обнаружена,
   заявка подтверждена, статус сменён…). Фичи подписываются: уведомления, массовость, отчёты, журнал.
   События же пишутся в журнал — одним механизмом закрываем аудит.
4. Порты и адаптеры для всего внешнего: LLM, эмбеддинги, речь, изображения, CMDB, история заявок,
   уведомления. У каждого порта реализации: заглушка/кэш, облако (Polza), локально. Выбор — конфигом,
   переключатель «облако / закрытый контур» виден в интерфейсе.
5. Данные, а не код: справочники, поля заявки, шкала приоритетов, SLA, регламент аварий, порог
   уверенности, порог массовости, структура исполнителей. Новое поле заявки = запись в реестре полей,
   промпт извлечения и форма диспетчера строятся из реестра автоматически.
6. Промпты — отдельные версионируемые файлы, не строки в коде. Ответ модели всегда валидируется по схеме,
   при ошибке — повтор, затем запасной путь (правила / кэш).
7. Модули фич. Каждая фича — папка со своими: шагами пайплайна, подписчиками событий, API-маршрутами,
   страницами и виджетами интерфейса, сид-данными, тестами. Подключение — одна строка в манифесте
   модулей + флаг. Укажи, что в модуле обязательно, а что нет.
8. Интерфейс. Реестр страниц и виджетов (дашборд и карточка заявки собираются из виджетов, модуль
   может добавить свой), дизайн-токены и общий набор компонентов, чтобы «вау»-стиль не разъезжался между
   агентами.
9. Отчёты. Отчёт = { запрос-метрика (считает код), визуализация, вывод «что это значит / что сделать»
   (формулирует ИИ по цифрам) }. Новый отчёт О1–О8 = новый модуль отчёта.
10. Оценка качества. Тестовый набор и оценщик метрик (К2) — отдельный модуль, гоняет тот же пайплайн;
    новые шаги автоматически попадают в оценку, если у них есть эталон.

Для каждой точки проверь на 3–4 идеях из банка (например: скриншот ошибки, Telegram-бот, прогноз нагрузки,
отчёт «пробелы базы знаний»): «как это добавится? какие файлы трогаем?». Если ответ «правим ядро» —
дорабатывай точку расширения.

ЧТО СДЕЛАТЬ
Шаг 1. Вопросы владельцу ОДНИМ блоком (не больше 5), только то, без чего нельзя решить и чего нет
в документах. К каждому — свой вариант по умолчанию, чтобы можно было ответить «да». Владелец занят
брейнштормом: не ждёшь ответа — идёшь с вариантами по умолчанию и помечаешь их «по умолчанию, ❓ подтвердить».

Шаг 2. Спецификация docs/specs/case9-core.md:
- архитектура: компоненты, слои, направление зависимостей, схема (mermaid) — она же пойдёт на слайд
  «Архитектура» (несколько ИИ-моделей, адаптеры, закрытый контур);
- структура репозитория (монорепо): пакеты и папки так, чтобы параллельные агенты не трогали одни файлы;
  отдельно — какие файлы «общие» (контракты, манифест модулей) и правило работы с ними;
- все 10 точек расширения выше: интерфейсы (сигнатуры на TS), где лежат, как регистрируются;
- модель данных (таблицы, ключевые поля, связи), статусы заявки и переходы, роли и права (на сервере);
- контракт ответа ИИ-разбора (схема): поля + уверенность + цитата, недостающие поля, признаки аварии,
  тональность, черновик уточняющего вопроса; валидация и что при ошибке;
- шаги пайплайна ядра по порядку; детектор аварии (правила + модель) и массовости; маршрутизация с
  объяснением; поиск по базе знаний (эмбеддинги); порог уверенности;
- API (эндпоинты, вход/выход), поток событий для интерфейса;
- режим стабильного демо: кэш ответов модели, запасной путь без сети, флаги фич;
- метрики качества (К2) и замер «с ИИ / без ИИ» (К4);
- синтетические данные: что генерируем, объёмы, как сидируем (сид — тоже по модулям);
- тесты и качество кода: линтер, strict TS, покрытие, SonarQube локально, тест-контракт для модулей
  (каждый модуль проходит общий набор проверок регистрации);
- раздел «КАК ДОБАВИТЬ ФИЧУ» — пошаговый рецепт на одну страницу: какую точку расширения выбрать,
  какие файлы создать, что зарегистрировать, какие тесты написать. Это главный документ для будущих фич.
Решения с альтернативами — коротко: «выбрали X, потому что…; отвергли Y, потому что…».

Шаг 3. Шаблон мини-спецификации фичи docs/specs/feature-template.md: что делает (для кого, какой критерий
закрывает), какие точки расширения использует, новые данные / события / шаги / экраны, файлы модуля,
флаг, тесты, момент в демо. Не больше одной страницы — фичу из брейншторма должны оформлять за 10 минут.

Шаг 4. План docs/plans/case9-core.md с ПАРАЛЛЕЛЬНЫМИ потоками (3–4), у каждого свои папки.
- Поток 0 (первый, короткий, блокирует остальные): каркас монорепо + пакет контрактов + каркас ядра
  с точками расширения (пустые реестры, шина событий, порты с заглушками) + тест-контракт модулей.
- Дальше параллельно: (а) пайплайн ядра на ЗАГЛУШКЕ модели (готовые ответы для 10 тестовых обращений)
  + сид-данные; (б) интерфейс от тех же контрактов на моковом API; (в) данные и тестовый набор + оценщик.
- Обязательные функции брифа (чат с уточнениями, авария + массовость, проверка диспетчером, исполнитель,
  база знаний, отчёт О0, «с ИИ / без ИИ») оформи КАК МОДУЛИ — это проверка, что точки расширения работают.
- К первому чекпоинту менторов работает сквозной путь «текст → заявка».
```
